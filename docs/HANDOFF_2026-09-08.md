## 3. Feature: event-driven trigger engine

**Chosen for the next session.** Gap analysis `docs/GAP_ANALYSIS_2026-07-13.md` §"Trading
engine & market data", P1, effort L.

### Correct the premise first

The gap doc says trigger evaluation runs on `IntervalTrigger(seconds=20)`. **That is stale.**
The scheduler now uses `settings.order_monitor_interval_s`, which defaults to **5.0**
(`config.py:166`). So the real gap is 5s → tick-driven, not 20s → tick-driven. The argument
still holds — 0DTE premiums move 30-50% inside seconds and a late stop is a different product
— but the spec and any user-facing claim should use the true number.

### The scaffold is better than the doc suggests

- `services/realtime_feed.py` already defines the exact hook needed: `RealtimeFeed.on_quote(handler)`
  (ABC at `:117`, live implementation `AlpacaRealtimeFeed.on_quote` at `:315`), plus
  `LatestStore` (`:181`) and a `FeedQuote` type (`:50`).
- It is already started in the `main.py` lifespan and already read through by
  `alpaca_client.get_quotes` (`:147-233`).
- It ships inert because `realtime_feed_enabled` defaults **False** (`config.py:58`), so
  `get_realtime_feed()` (`:511`) returns `NoOpRealtimeFeed`.
- The module's "equities only — alpaca-py 0.21.0 lacks `OptionDataStream`" comment
  (`:15-16`) is **stale**: `uv.lock` pins alpaca-py 0.43.4, which has `OptionDataStream`.

So the work is wiring and concurrency, not building a feed.

### The blocking design constraint

`run_order_monitor` (`order_monitor.py:777`) has **no internal lock**. Its only mutual
exclusion is APScheduler's `max_instances=1` on the `monitor_orders` job. A quote-driven
caller would run on the feed's thread concurrently with the cron pass and **double-book
fills** — the same working order filled twice, brackets closing a position already closed.

Do not wire `on_quote` → `run_order_monitor` without solving this. Recommended shape:

1. Add a module-level `threading.Lock` in `order_monitor.py` and have `run_order_monitor`
   acquire it **non-blocking** (`acquire(blocking=False)`); if it can't, return a summary
   marked skipped. The cron becomes the floor/safety net, the feed the fast path, and
   neither can overlap. Keep the lock re-entrancy story simple — one lock, one entry point.
2. Debounce/coalesce on the feed side. A liquid 0DTE symbol can emit hundreds of quotes/sec;
   a full monitor pass per quote is not viable. Evaluate at most every N ms per symbol, and
   only for symbols that actually have open/working trades.
3. Keep evaluation off the feed's I/O thread if a pass can block, or the stream falls behind
   and you lose the very latency you're buying.
4. Fix §2 item 3 (the write lock held across Alpaca calls) **first**. Raising trigger
   frequency against a database-wide lock that is already causing `database is locked` under
   a 5s cron will make that failure mode common rather than occasional.

### Scope decisions to make explicitly

- Which triggers go tick-driven: stops/trailing/brackets/premium exits are the value; MLL/DLL
  auto-liquidation is the highest-stakes and the most dangerous to get wrong.
- Gap-through fill policy: today fills price at the mark seen on the pass
  (`_entry_fill_price:1573`). Tick-driven evaluation makes "what price does a gap fill at"
  a real, answerable question — and a user-visible fairness promise.
- Whether to enable options streaming (`OptionDataStream`) or start with the equity
  underlying only. Underlying-driven triggers (bracket levels are on `entry_underlying`, see
  `_bracket_triggered:299`) get most of the benefit for much less risk.
- Feature-flag it. `realtime_feed_enabled` already exists; add a separate flag for
  tick-driven evaluation so the feed can be on while evaluation stays on the cron.

### Test surface

The monitor is heavily tested and the suite is deterministic — `run_order_monitor` takes
injectable `now`, `spot_for`, `option_mark`, `unrealized_for`, `market_open`, and
`session_factory`, so tick-driven paths can be tested without real time or network. Cover at
minimum: the non-blocking lock actually prevents overlap; a coalesced burst of N quotes
produces exactly one pass; a tick-driven stop and a cron-driven stop book identical results;
and the feed being down degrades to cron-only rather than to no evaluation.
